# `polymer-build` Security and Maintenance Assessment

**Audience:** dCache development team, team lead, release manager, and dCache View module importer/maintainer  
**Date:** 2026-08-07  
**Scope:** `modules/dcache-view` and its use in dCache FHS, tar, and system-test packages  
**Status:** Decision required

## Executive summary

The dCache View module declares `polymer-build@3.1.4` as a development dependency and invokes it from `gulpfile.js` to analyze and bundle a legacy Polymer 2 application based on Bower and HTML Imports. Version 3.1.4 is the newest published `polymer-build` release, but it was released in April 2019. There is therefore no available in-place upgrade that preserves the current build API while bringing the dependency onto a maintained release line.

A local `npm audit` on 2026-08-07 reported 43 findings across the complete dCache View npm development dependency graph: 7 critical, 25 high, 9 moderate, and 2 low. `polymer-build` is the only direct dependency reported as vulnerable and is rated critical through vulnerable transitive packages including `polymer-bundler`, `html-minifier`, `sw-precache`, `uuid`, and `vinyl-fs`. Not all 43 findings are necessarily attributable exclusively to `polymer-build`; the inventory must be reconciled with GitHub's current Dependabot/dependency-scanning alerts before closure.

The normal Maven assembly packages the checked-in, prebuilt files under `src/main/js`; it does not package `node_modules`, the Bower authoring tree, or the output under `target`. Consequently, an administrator installing an official binary RPM or tar archive is not expected to execute or receive `polymer-build`. The principal direct exposure is on developer and CI/release build hosts when the opt-in Maven `frontend` profile is activated. A compromised build host or dependency can, however, affect generated artifacts and therefore become a downstream supply-chain risk.

The preferred resolution depends on one product decision:

1. **If dCache does not need to regenerate this legacy frontend from its authoring sources, retire the frontend toolchain and ship the reviewed prebuilt assets.** This is the shortest path to removing the vulnerable npm build graph.
2. **If dCache must retain reproducible frontend rebuild capability, migrate the application from Bower/HTML Imports/Polymer 2 to maintained npm packages, ES modules, and a supported bundler.** Replacing `polymer-build` alone is not sufficient.

Until that decision and remediation are complete, frontend builds should remain isolated, non-root, network-controlled, and limited to trusted inputs. This containment reduces exposure but does not resolve the dependency findings.

## Current implementation

### Authoring and build path

The active frontend build is defined as follows:

- `package.json` declares `polymer-build@3.1.4`, Gulp, Bower, `merge-stream`, and `del` as development dependencies.
- `gulpfile.js` creates a `PolymerProject`, reads `polymer.json`, discovers source and dependency files, and invokes `polymerProject.bundler()`.
- `polymer.json` identifies `src/index.html` as the entry point, `src/elements/elements.html` as the shell, and requests an ES6 bundled build.
- The application is Polymer 2 and uses Bower-managed HTML Imports extensively.
- The Maven `frontend` profile installs a pinned Node/npm toolchain, runs `npm ci`, runs the project-local Bower executable through an npm script, and invokes the project-local Gulp executable through `npm run build`.

The `HtmlSplitter` stages in `gulpfile.js` currently split and immediately rejoin inline content without applying an intervening transformation. They appear redundant, but removing them does not remove the need for dependency analysis and HTML Import bundling.

### Packaging path

The normal Maven artifact and distribution path differs from the authoring path:

- `src/main/assembly/dcacheview-jar.xml` packages `src/main/js`.
- `src/main/js` contains 116 tracked files, including a checked-in, approximately 2.27 MB bundled `elements/elements.html` marked as generated by Polymer Bundler.
- No files under `node_modules` or `src/bower_components` are tracked or included by the dCache View assembly.
- FHS, tar, and system-test assemblies unpack the resulting `org.dcache:dcache-view` JAR into their respective `dcache-view` installation directories.
- The Maven `frontend` profile is opt-in. It is activated, for example, by adding `frontend` to a package build: `-P rpm,frontend`.

This split means that the frontend build can run without its generated output becoming the input to the Maven artifact. That should be treated as a correctness and reproducibility concern independently of the security findings: the repository currently contains both authoring sources and a separately checked-in release bundle, without an enforced equivalence check.

## Security and safety issues

### 1. No maintained upgrade path for `polymer-build`

`polymer-build@3.1.4` is the latest published release and dates from 2019. It is not marked deprecated in npm metadata, but the absence of subsequent releases means known vulnerable transitive dependencies cannot be resolved by selecting a newer supported `polymer-build` version.

`npm audit` suggests `polymer-build@2.2.0` as an available fix. This is a downgrade across a major version, conflicts with the current 3.x API expectations, and is not an acceptable remediation without a complete compatibility and security evaluation. Automated `npm audit fix --force` must not be used as a release remedy.

### 2. Critical build-time dependency chain

The direct critical finding is composed from these immediate paths:

```text
polymer-build@3.1.4
├── html-minifier@3.5.21
├── polymer-bundler@4.0.10
├── sw-precache@5.2.1
├── uuid@3.3.2
└── vinyl-fs@2.4.4
```

Reported downstream classes include arbitrary code execution in legacy Babel traversal, regular-expression denial of service, prototype pollution, unsafe parsing, and vulnerable file/path handling. Exact exploitability varies by package and by whether an attacker can influence source files, dependency contents, paths, or build configuration. The critical distinction is that this code executes on build hosts with the permissions and credentials of the Maven/CI user.

### 3. Legacy package acquisition

The application also depends on Bower and GitHub-hosted legacy component repositories. There is no Bower lockfile equivalent to `package-lock.json`, and the dependency graph includes old repositories and version ranges. A clean build may therefore be non-reproducible or fail as repositories, tags, Git protocols, and hosting behavior change.

The npm lockfile constrains npm package resolution, but it does not make Bower acquisition reproducible. Pinning Node and npm and using `npm ci` improves npm reproducibility only.

### 4. Supply-chain rather than installed-runtime exposure

For official binary packages, `polymer-build` is not a runtime dependency and is not expected to be installed on the dCache server. This materially lowers direct exposure of site administrators to the individual npm advisories.

It does not eliminate risk:

- Developers and CI/release workers that activate `frontend` execute the vulnerable graph.
- Source-based downstream packagers may activate the profile and execute it in their own environment.
- A vulnerable or compromised build can alter the checked-in/generated frontend artifact later distributed to sites.
- Build jobs may have access to repository credentials, artifact-signing material, package repositories, caches, or other sensitive workspace files.
- GitHub dependency scanning correctly continues to report vulnerable repository dependencies even when they are development-only and absent from the installed runtime.

### 5. Broad audit count needs ownership and reconciliation

The current audit count covers the full npm development tree, including Bower and other build tools. It should not be represented as 43 vulnerabilities caused solely by `polymer-build`. The release manager or security owner should export the current GitHub alerts and map each alert to one of:

- removed with `polymer-build` retirement;
- removed only with broader Bower/Gulp migration;
- independently remediable by a safe direct upgrade;
- accepted temporarily with documented scope, exploitability, owner, and expiration date.

## Questions requiring answers

The following questions should be answered before selecting a remediation path.

### Product and maintenance questions

1. Under what circumstances is dCache View rebuilt from `src/index.html` and `src/elements`, rather than shipped from the checked-in `src/main/js` bundle?
2. Which branch, repository, or team is authoritative for dCache View authoring sources?
3. Who is responsible for importing or refreshing `src/main/js`, and what verification is performed during that import?
4. Are changes still made to the legacy frontend source, or is the module effectively frozen?
5. Is retaining source-level rebuild capability a contractual, licensing, distribution, or project-policy requirement?
6. Must official releases be reproducible from source without relying on checked-in generated artifacts?

### Release and packaging questions

7. Is the `frontend` Maven profile used by official release jobs, nightly CI, developer builds, downstream distribution builds, or only manually?
8. Does any supported command assume that the Gulp-generated `target` directory is deployed directly?
9. Why does the Maven JAR package `src/main/js` rather than the output generated by the `frontend` profile?
10. Is there currently any test proving that regenerated output is equivalent to the checked-in packaged bundle?
11. Are the npm and Bower dependency trees included in source RPMs, source tarballs, SBOMs, or other deliverables even though they are absent from binary runtime packages?

### Site and threat-model questions

12. Do any site installers build dCache from source with `-P frontend`, or do supported installation procedures use only official binary packages?
13. If sites build from source, does the build run as root or with access to production configuration, credentials, package-signing keys, or shared caches?
14. Do official CI/release frontend jobs have outbound network access and access to secrets beyond what dependency acquisition requires?
15. Does the project security policy require critical/high development-dependency findings to block release even when the packages are not shipped at runtime?
16. Which GitHub dependency-scanning findings are open today, and what release deadline or service-level objective applies to them?

## Alternatives

### Option A: Retire the legacy rebuild path

**Use when:** dCache can treat the reviewed `src/main/js` assets as the supported distributable and does not need to regenerate them in this repository.

#### Work

1. Confirm that official and downstream package builds consume only `src/main/js`.
2. Record the provenance, license information, and review procedure for the checked-in bundle.
3. Remove the Maven `frontend` profile.
4. Remove `package.json`, `package-lock.json`, `.npmrc.build`, `gulpfile.js`, and `polymer.json` if they have no remaining purpose.
5. Remove or archive the unbundled authoring sources and Bower manifest if the project does not intend to maintain them. If retained for reference or source-compliance reasons, clearly mark them as non-buildable archival sources and keep vulnerable package manifests out of active dependency scanning where policy permits.
6. Update documentation so no supported workflow instructs users to run Bower/Gulp or deploy `target`.
7. Add package-level tests that verify expected frontend files and checksums or functional browser behavior in FHS/RPM/tar artifacts.
8. Generate a fresh SBOM and verify that `polymer-build`, Bower, and their npm dependency trees are absent.

#### Benefits

- Removes the vulnerable build dependency graph quickly and completely.
- Eliminates Bower network resolution and legacy build-host exposure.
- Reduces maintenance burden and release variability.

#### Costs and constraints

- The bundle cannot be regenerated in this repository.
- Checked-in generated JavaScript/HTML requires explicit provenance and review controls.
- Future frontend fixes require importing a new trusted prebuilt artifact or restoring a modern source build elsewhere.
- This option may be incompatible with source-reproducibility or distribution policy.

#### Security outcome

This option can resolve all npm findings associated solely with the retired frontend build graph. A post-change audit and GitHub alert review must confirm whether any npm manifests remain elsewhere.

### Option B: Retain rebuild capability by modernizing the frontend

**Use when:** dCache must be able to modify and reproducibly rebuild dCache View from source.

A substitution from `polymer-build` to Polymer CLI is not a solution because Polymer CLI uses `polymer-build` internally. Similarly, replacing only Gulp leaves the Polymer/Bower/HTML Imports dependency model intact.

#### Work

1. **Baseline behavior and artifact contents.** Capture browser workflows, supported browsers, API calls, generated bundle contents, CSP behavior, bundle size, and load performance.
2. **Inventory the application.** Catalogue all HTML Imports, custom dCache components, Bower repositories, inline scripts/styles, asset URL rewriting, Web Components polyfills, and components embedded in the generated bundle.
3. **Establish tests.** Add browser smoke and regression tests covering authentication, namespace browsing, upload/download, metadata, sharing, QoS, and error handling as applicable.
4. **Move dependencies to maintained sources.** Replace Bower dependencies with pinned npm packages or maintained internal packages. Fork only components that must be preserved and establish clear ownership and update policy.
5. **Convert module format.** Replace HTML Imports with ES modules. Migrate Polymer 2 elements to maintained Web Components, preferably Lit or another project-approved framework. Avoid merely repackaging obsolete components without maintenance ownership.
6. **Adopt a supported build tool.** Use a maintained ESM-native build pipeline such as Vite or current Rollup, with locked versions, integrity-protected installation, and minimal plugins.
7. **Make generated output authoritative.** Configure Maven to package the output produced in the same reactor build rather than a separately checked-in bundle, or implement a reproducible-build comparison if generated files must remain checked in.
8. **Harden CI.** Build as an unprivileged user in an ephemeral environment, limit outbound network access, isolate caches, expose no signing credentials during dependency installation, and sign only artifacts that pass tests and scanning.
9. **Remove the legacy stack.** Delete `polymer-build`, Polymer Bundler, Bower, old source bundles, and obsolete scripts only after behavior and packaging parity are demonstrated.
10. **Close findings with evidence.** Run npm audit, GitHub dependency review, SBOM generation, license review, and browser tests against the final packaged artifact.

#### Benefits

- Preserves maintainable source rebuild capability.
- Can resolve the entire vulnerable legacy frontend dependency model rather than suppressing alerts.
- Aligns package contents with the build performed by Maven.
- Enables future frontend security and functional maintenance.

#### Costs and constraints

- This is an application migration, not a dependency bump.
- Legacy Polymer and custom dCache components may require substantial conversion and regression testing.
- UI behavior, browser compatibility, and generated asset paths can change.
- Work requires an assigned frontend owner and coordinated release planning.

#### Security outcome

This is the preferred long-term option when rebuild capability is mandatory. Completion should require no unresolved critical/high findings in the maintained frontend graph, subject to the project's documented exception policy.

### Option C: Maintain a security-supported internal fork as a bridge

**Use when:** rebuilding is mandatory, migration cannot finish before the current release requirement, and the organization can commit engineering ownership to a temporary fork.

#### Work

1. Fork `polymer-build` and the minimum necessary Polymer tooling under an organization-controlled namespace.
2. Replace or patch vulnerable transitive dependencies and adapt APIs where major upgrades require code changes.
3. Add unit, fixture, and byte/semantic output-comparison tests against representative dCache View builds.
4. Publish immutable internal packages with provenance and restricted publishing rights.
5. Pin every npm and Bower/Git dependency; vendor dependencies that can no longer be acquired reproducibly where licensing permits.
6. Run builds in the hardened environment described above.
7. Set an explicit retirement release and owner for the fork.

#### Benefits

- May reduce immediate findings while preserving legacy output.
- Creates a controlled transition window for Option B.

#### Costs and constraints

- The team becomes maintainer of obsolete parsing, transformation, and bundling software.
- Upgrading old transitive dependencies may introduce subtle output incompatibilities.
- Broad npm `overrides` alone are unsafe because they bypass declared compatibility without proving behavior.
- This path can consume substantial effort without delivering a maintainable frontend.

#### Security outcome

Potentially acceptable only as a time-bounded bridge. It resolves findings only when patched packages are demonstrably non-vulnerable and GitHub/audit scanners recognize the fixed versions. Alert suppression without code remediation is not resolution.

### Option D: Continue with containment and documented exceptions

**Use when:** only as a short, explicitly approved interim state while Option A, B, or C is executed.

#### Controls

- Run frontend builds only in disposable, unprivileged CI containers or workers.
- Do not build as root or on a production dCache host.
- Provide only read access to source and a dedicated write-only artifact destination where practical.
- Keep signing keys and deployment credentials out of dependency-install and frontend-build stages.
- Restrict egress to required npm/Git endpoints or use an approved repository proxy.
- Continue using pinned Node/npm, project-local executables, `npm ci`, an isolated cache/prefix, and a lockfile.
- Scan the lockfile and generated artifact on every build.
- Record each exception with advisory, affected path, exploitability assessment, owner, approval, and expiry date.

#### Security outcome

Containment lowers likelihood and blast radius but leaves findings unresolved. It should not be presented to GitHub, auditors, or users as vulnerability remediation.

## Recommended decision and sequence

1. **Within one planning cycle:** answer Questions 1, 7, 9, 12, and 15. These determine whether the build is needed and who is exposed.
2. **Immediately:** classify official binary installation as distinct from source/frontend build exposure in release and security documentation. Harden any job that currently activates `frontend`.
3. **Preferred decision:** choose Option A if the legacy frontend is frozen and source rebuild capability is not required; choose Option B if it remains a maintained product component.
4. **Avoid an indefinite fork:** choose Option C only with a named owner, funded effort, and retirement milestone.
5. **Do not close alerts on containment alone:** Option D is temporary risk acceptance, not a fix.

A practical ownership model is:

| Responsibility | Proposed owner |
|---|---|
| Decide whether source rebuild capability is required | Team lead and dCache View/module owner |
| Confirm official and downstream release workflows | Release manager |
| Export and reconcile GitHub alerts | Security/dependency owner |
| Confirm importer provenance and update procedure | Developer responsible for module import |
| Approve temporary exceptions | Team lead and security/release authority |
| Implement retirement or migration | Assigned frontend/module maintainers |
| Validate packaged behavior | QA/system-test owner and release manager |

## Acceptance criteria

The issue is resolved only when the criteria for the selected path are met.

### Common criteria

- No supported build documentation invokes an obsolete or removed path.
- A clean build from a fresh workspace produces the intended FHS/RPM/tar contents.
- Browser smoke tests pass against the packaged artifact, not merely a development server.
- The SBOM accurately distinguishes build-time and shipped runtime components.
- GitHub dependency alerts are closed by dependency removal or verified remediation, not unexplained dismissal.

### Option A criteria

- No active npm/Bower manifest in this module references `polymer-build` or its legacy toolchain.
- Official artifacts contain only the approved prebuilt frontend and required runtime assets.
- Provenance and update ownership for the prebuilt frontend are documented.

### Option B or C criteria

- The frontend is reproducibly generated from source using locked dependencies.
- Maven packages that generated output or verifies exact equivalence with checked-in output.
- No unresolved critical or high vulnerabilities remain in the maintained frontend dependency graph unless covered by a formally approved, expiring exception.
- Build jobs run with least privilege and do not expose release secrets during dependency installation.

## Evidence and limitations

This assessment is based on repository inspection and a local `npm audit` performed on 2026-08-07. Advisory data and GitHub alert state can change. Before a release decision, the team should retain:

- the current GitHub Dependabot/dependency-scanning export;
- the complete `npm audit --json` output from the pinned build environment;
- an SBOM for both source/build dependencies and the packaged runtime artifact;
- CI logs showing whether the `frontend` profile ran;
- package-content inspection proving whether npm/Bower files were shipped;
- browser test results for the actual FHS/RPM/tar output.

A transient local dependency-installation failure occurred early in the investigation, before npm was isolated from user-level configuration. It is not treated as a product defect or as evidence against `polymer-build`; its relevance is limited to demonstrating why frontend builds need project-scoped configuration and a reproducible, clean build environment.
